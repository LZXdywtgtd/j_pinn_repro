# 开发工作流（完整版）

> J-PINN 团队 / 开发工作流参考
> 风格仿 [v4 流程.md](../../projects/pe_mmnet/project_v4/docs/流程.md)

本文档定义**需求澄清 → 技术规划 → 开发/修复 → 审计 → 更新文档 → 原子提交 → 等待授权推送**的完整闭环。所有代码变更必须走完此流程。

> **核心原则**：**文档是 commit 前的最后一道审计**——写文档时再次核对参数，能发现代码 bug。

---

## 双循环总览

```
[ 输入需求 ] → [ 询问细化 ] → [ 输出计划 ] ← 规划环（阶段0）
                         ↓
              (计划通过，进入执行环)
                         ↓
         修复/开发代码 → 审计代码（4 维度）→ 自动修复 → 再审计（无问题）
                          ↓                               ↓
                          问题 ←────────────────────────────┘
                          ↓
                     写文档（每个函数详细，参数与代码对齐）→ 再审计文档
                          ↓
                     原子提交 → 等待授权推送
```

| 阶段 | 产出 | 核心规则 |
|------|------|----------|
| 0. 规划 | 计划.md（方案/清单/风险/测试） | 必须澄清5大维度，否则不编码 |
| 1. 开发 | 改动的 .py | 本地冒烟测试无语法错误 |
| 2. 审计 | 审计报告（4 维度核对） | 仿 v4 文档审查指南 §三 |
| 3. 修复 | 改动的 .py | 自动修复审计发现的问题，循环回 2 |
| 4. 文档 | 改动的 .md（每个函数详细） | **写文档时核对代码签名/参数**——审计用途 |
| 5. 提交 | 1 个原子 commit（含代码+小文档） | **不攒 commit，一个改动一个 commit** |
| 6. 推送 | `git push origin main` | **commit 由我做，push 由你决定时机** |

---

## 各阶段详述

### 阶段0：开发策划（需求 → 计划）

在进入"修复/开发代码"之前，所有新功能、重构或非紧急修复必须先走完本阶段。

#### 0.1 需求输入
- 接收自然语言需求（如："新增动态学习率调度器"、"修复显存泄漏"）。
- 记录原始需求，不进行主观猜测。

#### 0.2 询问细化（深度澄清）
必须主动向需求方提出以下 5 大维度的澄清问题（可复用检查清单）：

| 维度 | 核心问题 | 目的 |
|------|----------|------|
| **目标（Why）** | 解决什么痛点？预期效果是什么？ | 对齐价值，避免过度设计 |
| **验收标准（What）** | 如何验证成功？具体指标/行为？ | 定义"完成"的边界 |
| **约束（Where）** | 是否受限于特定设备/环境？是否有性能阈值？ | 限制技术选型范围 |
| **影响范围（Who）** | 涉及哪些现有模块？是否向后兼容？ | 规避回归风险 |
| **优先级（When）** | 是 Hotfix（立刻执行）还是正常迭代？ | 决定是否跳过分阶段 |

> **约定**：提问必须得到明确答复，否则不允许进入"计划"阶段。

#### 0.3 输出技术计划（Plan结束）
产出结构化计划（直接写入 `docs/dev_reference/开发计划模板.md` 或当前 Issue 中），包含：

1. **方案设计**：核心思路（如：新增 `schedulers/dynamic_lr.py`，修改 `trainer.py` 调用位置）
2. **变更清单**：预计修改的文件列表（`train.py`、`models/...`、`docs/...`）
3. **风险与回滚**：可能影响哪些旧功能？回滚方案是什么？
4. **测试策略**：如何验证（单元测试 / Smoke Test / 手动跑一次完整训练）？

> **注**：由于不使用 PR 流程，计划确认后**直接在当前分支（main）上开发**；若涉及跨日大型特性，可新建 `feature/` 分支，但基础开发步骤不变。

### 阶段1：修复/开发代码

- 修改 `train.py` / `losses.py` / `models/` / `data/` / `utils*.py` / `visualize.py` 等。
- 改完后**必须**立即在本地跑冒烟测试：`python tests/smoke_test.py`
- 如涉及新的 CLI flag，同步在脑里记下：默认值、类型、是否被代码实际使用。

### 阶段2：审计代码（4 维度核对）

仿 [v4 docs/文档审查指南 §三](../../projects/pe_mmnet/project_v4/docs/文档审查指南.md) 的 5 大维度，本项目精简为 4 维度：

| 维度 | 核对内容 |
|------|----------|
| **准确性** | 函数签名/默认值/参数名/返回值 与源码 100% 一致；CLI flag 实际生效 |
| **完整性** | 测试覆盖核心路径（端到端 + 单元）；无 dead code；无遗漏分支 |
| **一致性** | 与 v4 风格对齐（Adam + CosineAnnealing + 梯度裁剪 + Tee 等）；CLI 默认值与 dataclass 默认值一致 |
| **时效性** | 文档（api.md / 流程.md / CHANGELOG.md）与代码同步；旧描述无残留 |

**审计产出**：
- 每个问题标注 CRITICAL / HIGH / MEDIUM / LOW + 行号 + 修复建议
- 不通过审计 → 进入阶段3 修复
- 通过审计 → 进入阶段4 文档

### 阶段3：自动修复（迭代回 2）

- 按审计报告逐条修复（优先级：CRITICAL → HIGH → MEDIUM → LOW）
- 修复后**必须**重新审计（迭代回 阶段2）
- 直到审计无 CRITICAL/HIGH 问题，才进入阶段4 文档
- 已知但暂时不修的 LOW 问题，**记入 `docs/CODE_BUGS.md`**

### 阶段4：写文档（每个函数详细 + 参数对齐审计）

**核心原则**：**写文档时再次核对代码**，能发现审计遗漏的 bug。

具体执行：
1. **每个公开函数/类**必须有完整 docstring：签名 + 参数 + 返回值 + 异常
2. **每个 CLI flag**必须在 `api.md §5.1` 列出：默认值 + 类型 + 用途
3. **每个新文件**必须在 `architecture/架构设计文档.md` 注册
4. 每次写完一段文档，**回到代码核对**（grep 函数名 → 看签名 → 校对文档描述）
5. 旧版本移到 `docs/archived/YYYY-MM-DD-1/`（不删，留回滚路径）

#### 文档地图（J-PINN 项目）

| 文档 | 角色 |
|------|------|
| `README.md`（根） | 项目入口 + 训练状态表 + 快速开始 |
| `CHANGELOG.md`（根） | 版本历史（fix/feat/refactor） |
| `docs/全流程.md` | 本文件：开发工作流完整版 |
| `docs/CODE_BUGS.md` | 已知但不修的 bug 清单 |
| `docs/文档审查指南.md` | 文档维护指南 + 文档地图 |
| `docs/user_guides/快速配置指南.md` | 首次使用 + CLI flag 速查 |
| `docs/architecture/架构设计文档.md` | 4 区域 JPINN + 损失组合 |
| `docs/dev_reference/api.md` | 公开 API 函数签名 |
| `docs/dev_reference/开发人员文档.md` | 开发者上手 + 添加新变体 |
| `docs/experiment_reports/调参与算法工程指导文档.md` | 损失函数 + 超参 |
| `docs/experiment_reports/项目算法与训练实验设计报告.md` | 算法原理 + 实验设计 |
| `docs/archived/` | 旧版本存档 |

### 阶段5：原子提交（commit）

**提交粒度**：**每个独立改动一个 commit**（原子提交）。

- 不允许将多个不相关改动攒在一个 commit 中。
- 伴随性的小文档更新（如修改了 CLI 描述）合并入 code commit。
- **只有大范围文档重写**才单独开一个 `docs:` commit。

**Commit message 规范**：

```bash
git commit -m "fix|feat|refactor|docs|perf|chore(<scope>): 简短标题"

# 空行后接详细正文，按以下结构展开（必须包含）：
# - 症状：遇到的问题或需求背景
# - 根因：导致该问题的根本原因（若为 bug 修复）
# - 修复/实现：做了哪些具体改动
# - 验证：如何验证（冒烟测试 / 本地训练结果）
# - 影响范围：可能影响的模块、是否向后兼容
```

**前缀规范**（参考 v4 历史风格）：
- `fix:` Bug 修复
- `feat:` 新功能
- `refactor:` 重构（行为不变）
- `docs:` 大范围文档改动（小范围文档随 code 提交时不使用此前缀）
- `perf:` 性能优化
- `chore:` 杂项（配置、脚本）
- 支持作用域：`feat(data):` / `fix(train):` 等

### 阶段6：等待授权推送（push）

**推送节奏**：**一个 commit 推一次**，不要攒多个 commit 一起推。

- **commit 由我做**：本地完成所有 commit 后，主动提示你检查。
- **push 由你决定时机**：你 review commit message 和改动后，授权我执行推送操作。
- 推送命令：
  ```bash
  git push origin main
  ```

**重要产物隔离**（`git add -A` 前必须确认）：
- 永远不入仓：`checkpoints/*.pt`、`logs/*.csv`、`logs/figures/`、`data/*.npz`、`__pycache__/`
- v0.9 新增：`outputs/`（自动归档目录，含 latest.json / model_best.pt / train_history.csv 等，已在 .gitignore）
- 使用 `.gitkeep` 保留空目录
- 论文 PDF 文件排除（学术版权 + 体积）

## 循环的边界

| 在循环内（规划环 + 执行环） | 在循环外 |
|---------------------------|----------|
| 所有明确需求的 Bug 修复 | 纯文本 typo 修复（可直接 commit，但需告知） |
| 新特性开发（走完整规划环） | 无代码变动的纯文档维护（如调整排版） |
| 性能优化 + 文档同步 | 跨多周的大型项目（需独立项目文档） |
| 紧急 hotfix（快速走规划环） | 仅由 CI 自动触发的依赖更新 |

### 验证文档交叉引用
```python
import os, re
for root, _, files in os.walk('docs'):
    for f in files:
        if f.endswith('.md'):
            path = os.path.join(root, f)
            with open(path, 'r', encoding='utf-8') as fp:
                content = fp.read()
            for link in re.findall(r'\]\(([^)]+\.md)\)', content):
                base = os.path.dirname(path)
                target = os.path.normpath(os.path.join(base, link))
                if not os.path.exists(target):
                    print(f'BROKEN: {path} -> {link}')
```
