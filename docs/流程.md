# 开发工作流

> J-PINN 团队/开发工作流参考
> 风格仿 [v4 流程.md](../../projects/pe_mmnet/project_v4/docs/流程.md)

本文档定义**修复 → 自检 → 更新文档 → 准备 commit** 的标准循环。每次代码变更都应走完这个循环。

---

## 循环总览

```
修复代码 → 自检（冒烟测试）→ 更新文档 → 准备 commit
   ↑                                          ↓
   └──────── 再次回到修复代码 ←────────────────┘
```

每个阶段产出的可交付物：

| 阶段 | 产出 | 工具/方法 |
|------|------|----------|
| 修复代码 | 改动的 .py / .md | 直接编辑 + `git diff` |
| 自检 | `tests/smoke_test.py` 通过 | `python tests/smoke_test.py` |
| 更新文档 | 改动的 .md | 逐文件对照代码（不追加、整体重写） |
| 准备 commit | 1 个或多个 commit | `git add` + `git commit`（**不 push**） |

**Push 由用户决定**（用户授权边界）。本地 commit 准备到任意阶段可暂停。

---

## 各阶段详述

### 1. 修复代码

- 修改 `train.py` / `losses.py` / `models/` / `data/` / `utils.py` / `visualize.py` 等
- 改完后立即在本地跑冒烟：`python tests/smoke_test.py`
- 如涉及新的 CLI flag，同步在脑里记下：默认值、类型、是否被代码实际使用

### 2. 自检（冒烟测试）

```bash
python tests/smoke_test.py
```

应输出 `✓ ALL SMOKE TESTS PASSED`。8 步：
1. 生成合成数据
2. 加载数据集
3. 构建 4 区域 JPINN（断言参数量）
4. 配点 batch 采样
5. Forward + 5 类损失
6. Backward + 梯度裁剪
7. 10 epoch mini-training
8. Checkpoint roundtrip

如有失败，按错误信息定位修复（详见 [CODE_BUGS.md](CODE_BUGS.md) 已知问题）。

### 3. 更新文档

**不追加、整体重写**（v4 用户约定）。每个 .md 都对照代码逐项核对。

具体流程：
1. 检查 [CODE_BUGS.md](CODE_BUGS.md) 中是否有本次新发现 bug
2. 同步更新相关文档：
   - CLI flag 改动 → [快速配置指南](../user_guides/快速配置指南.md) + [api.md](../dev_reference/api.md) + [调参指南](../experiment_reports/调参与算法工程指导文档.md)
   - 模型架构改动 → [架构设计文档](../architecture/架构设计文档.md)
   - 损失函数改动 → [架构设计文档](../architecture/架构设计文档.md) + [调参指南](../experiment_reports/调参与算法工程指导文档.md)
   - 公开 API 改动 → [api.md](../dev_reference/api.md)
   - 新 bug 发现 → [CODE_BUGS.md](CODE_BUGS.md)

### 4. 准备 commit

```bash
cd D:/team_project/j_pinn_repro
git status                                    # 确认无意外文件
git add <files>                                # 只 stage 相关文件
git commit -m "fix|feat|refactor|docs: ..."    # 简洁一行 + 详细 body
git log --oneline                              # 检查提交
```

**不执行 `git push`**——由用户决定推送时机。

---

## Commit message 规范

参考 v4 历史风格：

- `fix:` Bug 修复
- `feat:` 新功能
- `refactor:` 重构（行为不变）
- `docs:` 文档改动
- `perf:` 性能优化
- `chore:` 杂项（配置、脚本）
- 支持作用域：`feat(data):` / `fix(train):` 等

详细 body 用空行后块结构：

```
**症状**：...
**根因**：...
**修复**：...
**验证**：...
**影响范围**：...
```

---

## 循环的边界

| 在循环内 | 在循环外 |
|----------|----------|
| Bug 修复 + 文档同步 | 全新大型特性（独立分支 + PR 流程） |
| 性能优化 + 文档同步 | 重构（无 bug 触发，单独 commit） |
| 文档大改 | 纯文本 typo 修复（直接 commit） |
| 紧急 hotfix | 跨多周的项目 |

---

## 已知问题治理

每次进入循环时检查 [CODE_BUGS.md](CODE_BUGS.md)：

- 是否有 bug 被修复（更新状态从"已知"→"已修复"，注明 commit hash）
- 是否有新 bug（按相同 schema 追加）
- 是否有 bug 升级（影响扩大、改了优先级）

`CODE_BUGS.md` 同步入版本控制，作为团队"已知未修 bug"的可视化清单。

## 速查


### 验证文档交叉引用
```python
import os, re
for root, _, files in os.walk('docs'):
    for f in files:
        if f.endswith('.md'):
            path = os.path.join(root, f)
            with open(path, 'r', encoding='utf-8') as fp:
                content = fp.read()
            for link in re.findall(r'\]\(([^)]+\.md)\)', content):
                base = os.path.dirname(path)
                target = os.path.normpath(os.path.join(base, link))
                if not os.path.exists(target):
                    print(f'BROKEN: {path} -> {link}')
```
